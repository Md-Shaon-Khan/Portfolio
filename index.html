HealthBridge

An end-to-end ECG analysis system combining sensor-based signal acquisition, deep learning classification, clinical risk assessment and web-based reporting.

  • TensorFlow
  • Keras
  • Scikit-learn
  • FastAPI
  • MongoDB
  • Arduino
  • Signal Processing
  • Built the acquisition hardware around an Arduino UNO and AD8232 3-lead ECG sensor (RA, LA, RL), sampling at 360 Hz to match MIT-BIH and logging raw and moving-average filtered values as CSV to an SD card module over SPI.
  • Implemented the backend preprocessing for uploaded .csv/.txt recordings: interpolation of flat or clipped samples, 0.5–45 Hz bandpass filter, 50 Hz notch filter for mains interference, and z-score normalization per 10-second segment.
  • Integrated a ResNet1D classifier (TensorFlow/Keras) that takes 3600-sample windows and predicts 8 classes: Normal, Supraventricular, Ventricular, Conduction Disorder, Myocardial Infarction, Hypertrophy, Ischemia/ST-T and Atrial Fibrillation. Training data: MIT-BIH, PTB-XL and CPSC 2018.
  • Aggregated per-segment predictions and confidences into an overall top condition with average probability, and mapped abnormal segments to clock time when the recording start time is given.
  • Added a separate scikit-learn model for vitals-based prediction (temperature, heart rate, blood pressure, humidity and six symptoms) that returns a disease category, a 0–100% risk score and basic recommendations.
  • Developed the FastAPI backend with endpoints for signup/login, ECG and vitals prediction, report storage, patient search, doctor statistics and doctor-to-patient feedback, backed by MongoDB Atlas through the async Motor driver.
  • Built separate patient and doctor dashboards (HTML/CSS/JavaScript, Chart.js): patients upload ECGs, track report history and read prescriptions; doctors search patients, review vitals charts and ECG history, and send feedback.
  • Added a medical chatbot endpoint using LLaMA 3.3 70B through the Groq API.
  • Deployed the frontend on Netlify and the API on Render; the backend downloads the ECG model from Google Drive on startup.

Farmer's Friend

ongoing

A rice-leaf disease analysis platform using computer vision to identify disease categories and provide practical guidance in Bangla.

  • PyTorch
  • ConvNeXt-Tiny
  • MobileNetV3
  • Grad-CAM
  • OpenCV
  • FastAPI
  • Built a two-stage rice-leaf classification pipeline behind a FastAPI endpoint (POST /api/predict, image upload), so only images judged to be paddy reach the disease model.
  • Stage 1 is a MobileNetV3-Small gatekeeper at 224×224. If neither the paddy nor the not-paddy class reaches 0.85 confidence, the image is rejected as non-paddy.
  • Stage 2 is a ConvNeXt-Tiny fine-tuned at 384×384 with balanced fine-tuning. It predicts Bacterial, Fungal, Viral or Normal, so it reports pathogen type, not a specific disease name.
  • Added Grad-CAM localization: the predicted class is back-propagated through ConvNeXt, the heatmap is thresholded into contours, and numbered boxes are drawn on the leaf. The API returns the annotated image as base64 with per-spot metrics, only when a disease is predicted.
  • Added visual similarity search: ConvNeXt features give a normalized 768-d embedding per leaf, and cosine similarity against a reference gallery returns the top 5 matches. Gallery embeddings are computed once and cached to an .npz file.
  • Moved the notebook experiments into reusable backend modules (feature extractor, Grad-CAM spot detector, pipeline, response schemas); the frontend shows the prediction, marked spots and similar-leaf thumbnails.

UniFix

A Java-based campus issue management system connecting students with the appropriate university authority.

  • Java
  • JDBC
  • MySQL
  • NetBeans
  • Group project: a Java desktop application that gives students a formal channel to report campus problems and track them to resolution, replacing informal complaints that had no follow-up.
  • Students register, log in and submit issues by category (hall, department, security or general campus concerns).
  • Authorities get a dedicated panel listing issues for their department, where they post official responses and track resolution status.
  • A student who is unsatisfied with a response can follow up on the same issue instead of filing a new one.
  • Other students can see reported issues and register support for shared concerns, which keeps the process visible.
  • Role-based access (student, authority), with data held in MySQL (XAMPP/PHPMyAdmin) and accessed through JDBC, covering users, issues, responses, follow-ups and support.

LockGuard

A dual-factor electronic door-lock system designed using combinational and sequential digital logic without a microcontroller.

  • Logic Gate ICs
  • Keypad
  • Buzzer
  • Relay
  • Digital Logic Design course project: a dual-factor door access system built from discrete logic gate ICs, with no microcontroller or software stack.
  • Access is granted only when two independent authentication inputs are both satisfied; a mismatch or forced-entry condition triggers the alert output.
  • Designed combinational logic for the authentication decision and sequential logic for the lock and alert state transitions.
  • Output stage uses a relay for the lock, a buzzer for alerts and LED indicators on a breadboard or PCB build.
  • Documented the design with block and logic diagrams, truth tables, circuit analysis and testing in a full report.
